# Merge-by-ID: чек-лист включения (в продакшн)

Как безопасно перевести синхронизацию с legacy-пути на merge-by-ID
(см. `SERVER_SYNC_SPEC.md`). Выполняется только после деплоя сервера с
ops-контрактом.

## 1. Перед включением (подготовка)
- [ ] Убедиться, что клиент собран с текущим кодом (stable-id, canonical, diff-движок).
- [ ] Развёрнут сервер с `src/services/reportOpsService.js` и `reportsService.patchReportOps` (PATCH `/reports/:id` принимает `{ops:[...]}`).
- [ ] Отчётливый план отката: флаг возвращается в `false` без пересборки всех клиентов не выйдет — планировать канареечный деплой.
- [ ] Бэкап БД reports (на случай отката).

## 2. Решение по «замку» переводов (уже реализовано)
- [ ] Убедиться, что в UI есть диалог разблокировки с выбором:
  «уточнить формулировку (переводы сохраняются) / изменить и удалить переводы /
  добавить новый ответ / не менять ничего».

## 3. Включение (клиент)
- [ ] В `lib/providers/report_provider.dart` поменять:
  `static const bool mergeOpsEnabled = false;` → `true`.
- [ ] Пересобрать и выкатить web и мобильные сборки.
- [ ] Убедиться, что при 400/404/405 или отсутствии `merged` клиент автоматически
  падает на legacy-путь (фолбэк уже реализован).

## 4. Live-проверки (два клиента, один отчёт)
- [ ] Два пользователя одновременно добавляют **ответ** в один вопрос → у обоих
  ответы сохранены, дубликатов нет.
- [ ] Два пользователя одновременно добавляют **вопрос** → оба вопроса сохранены
  в детерминированном порядке.
- [ ] Правка **разных языков** одной строки → автослияние, без диалога.
- [ ] Правка **одной ячейки (rid+lang)** с одной базы → появляется диалог
  (принять серверный / заменить своим / сохранить как второй ответ),
  результат сохраняется после повторной отправки.
- [ ] «Уточнить формулировку» не удаляет переводы; «изменить и удалить переводы» —
  удаляет.
- [ ] Legacy-отчёт (schemaVersion 1): открывается, мигрируется, первый save
  «сеет» canonical полным документом, последующие — через ops.
- [ ] Параллельная миграция одного legacy-документа двумя клиентами → без
  дубликатов вопросов/строк (qid/rid-dedup + алиасы).
- [ ] Медиа: новое фото/видео получает `serverFileId`, затем `answer.setMedia`
  синхронизируется; удаление файла не оставляет «осиротевших» объектов.
- [ ] Share-ссылка (анонимный редактор) продолжает работать (legacy), либо — после
  реализации — через ops.

## 5. Метрики/наблюдение после включения
- [ ] Проверить логи сервера: `patchReportOps` применяется, 409 только по ячейкам.
- [ ] Контроль количества 409 в сутки (должно быть редким).
- [ ] Убедиться, что `version` отчёта растёт на каждый merge.

## 6. Откат
- [ ] Вернуть флаг в `false` и пересобрать клиентов.
- [ ] Сервер продолжает принимать и legacy-формат (обратная совместимость сохранена).
